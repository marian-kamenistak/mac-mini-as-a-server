# Pitfalls

Every row is a mistake I made while setting this up. Read it before you start: each one cost time.

| # | What I assumed | What was true | Fix |
|---|---|---|---|
| 1 | Scripts run with ssh see the same PATH as Terminal | A non-interactive SSH session has a PATH of only /usr/bin:/bin:/usr/sbin:/sbin, so `sudo npm` failed with "env: node: No such file". `timeout` (GNU coreutils) is also missing from it | `lib.sh` exports a full PATH at the top of every script |
| 2 | Installing a second Python version is harmless | Each python.org pkg re-points `/usr/local/bin/python3` to itself, so the last one installed wins | Link the version you want explicitly after all installs (`20-toolchain.sh`) |
| 3 | `python3` on the mini is the python.org one | Homebrew installs `python@3.x` as a dependency and links `/opt/homebrew/bin/python3`, which comes before `/usr/local/bin` in a typical job PATH. Jobs then run on brew's Python without your packages. An Intel Mac does not hit this, because its Homebrew lives in `/usr/local` | `brew unlink python@3.x` for each, then check `which python3` |
| 4 | "Security Responses: auto-install" is safe to leave on | With FileVault on, any unattended restart stops every job until someone unlocks the Mac locally. The first Tahoe Background Security Improvement restarted Macs without asking (eclecticlight.co, 17 March 2026) | Check and download only, never auto-install (`10-root.sh`). Update by hand, then check your jobs |
| 5 | MagicDNS names are fine for SSH and Screen Sharing | MagicDNS is unreliable on macOS Tahoe (github.com/tailscale/tailscale/issues/20890 and github.com/tailscale/tailscale/issues/21794) | Use the 100.x.y.z IP in `~/.ssh/config` and in `vnc://` URLs |
| 6 | Signing in to Tailscale with a work Google account gives you your own tailnet | If your company domain already has a tailnet owned by someone else, you get "user approval required", and that admin has to choose a plan | Use a personal identity that you own. Sign the browser in to that tailnet BEFORE you open the device link, or use an auth key |
| 7 | Test the ssh alias, not the machine: "ssh-copy-id mini" will just work | If the alias name does not resolve, `ssh-copy-id` stalls with no error | Run `nc -z <host> 22` before you hand over an ssh command |
| 8 | Without setting a hostname the machine has the name from Sharing everywhere | macOS had no `HostName` set, so `hostname` returned the router's DHCP name and Claude Remote Control named the environment after it | `sudo scutil --set HostName <name>` (`10-root.sh`), and pass a session name prefix to Remote Control |
| 9 | Turning on Remote Management is enough for Screen Sharing | The defaults allow "All users" and offer a legacy VNC password of 8 characters at most | Limit access to the one account, tick Observe and Control, turn the VNC password option OFF (RUNBOOK A3b) |
| 10 | The mini runs the same macOS major version as the laptop | It can ship with a newer one (macOS 27 on the mini, 26 on the laptop) | Re-check launchd, background items and Tailscale on the newer version. Keep both Macs on the same major version before moving jobs that share code paths |
| 11 | The mini is on Ethernet | It had joined Wi-Fi. The Ethernet port had no link, so LAN ping was 50 to 100 ms | Plug in Ethernet. It is also needed for reliable macOS pre-boot FileVault SSH unlock |
| 12 | The disk is big enough | A 256 GB SSD fills up with repos, node_modules, browser profiles and logs | Exclude node_modules and media where you can, and alert on free disk space |
| 13 | `claude auth status` over SSH shows whether the mini is logged in | Over SSH the login Keychain is locked, so it always says "Not logged in", even after a GUI `/login`. Only a LaunchAgent, which runs in the GUI session, is a real test. A fresh Mac also has no `~/Library/LaunchAgents` folder. Terminal windows opened before a PATH edit do not see `claude` | `60-claude.sh` treats the SSH check as information only, runs `mkdir -p ~/Library/LaunchAgents`, and lets a LaunchAgent smoke test decide. Open a new Terminal window after PATH edits |
| 14 | A Remote Control LaunchAgent starts as soon as you log in | It needs three one-time answers in a real terminal: folder trust (saved to `~/.claude.json` only when that session ends, so `/exit`), "Enable Remote Control? y", and no other `claude remote-control` serving that folder ("already served ... Stop it first") | RUNBOOK B8b: `claude` > Yes > `/exit`, then `claude remote-control` > y > Ctrl+C, then load the plist |
| 15 | `claude remote-control --spawn worktree` is a good default | Worktree spawning piles up worktrees, and the default `--capacity 32` is far more than a mini should serve (code.claude.com/docs/en/remote-control) | `--spawn same-dir --capacity 2`. Check `claude remote-control --help` for the spawn modes of your version |
| 16 | One `unset ANTHROPIC_API_KEY` in the job wrapper stops API billing | Jobs source `~/.env` again after the wrapper, so the key comes back | Keep the key out of the mini's env files (`50-secrets.sh` strips it), and use `env -u ANTHROPIC_API_KEY` in the command that starts `claude` |
| 17 | Setting no model is fine for a scheduled `claude -p` | It uses whatever `model` your `settings.json` names, which may be your most expensive one | Pass `--model` in every scheduled job and test for it |
| 18 | Copying a browser profile folder moves the logins | Cookies are encrypted with that Mac's Keychain ("Chrome Safe Storage"), so a copy opens logged out (github.com/openai/codex/issues/33287). Sites also flag a session used from two Macs | Never copy profiles. Log in again on the mini itself, from home, and keep one profile per site account |
| 19 | A profile logged in with plain Chrome works for the jobs | The jobs launch Chrome with their own flags (here `--use-mock-keychain --password-store=basic`). Cookies written by plain Chrome use the real Keychain and are unreadable to the job, so it looks signed out | Log in only through the job's own login command, then quit Chrome with Cmd+Q. Every launch must carry the same flags |
| 20 | `open -na "Google Chrome" --args --user-data-dir=<p> <url>` opens each profile on its login page | All windows opened blank, because first-run screens swallow the URL. Signing in to Chrome itself then turns on Google sync, which imports bookmarks and extensions into the robot profile | Send the URL by running the Chrome binary again with the same `--user-data-dir` (it opens a tab in the running window). Log in to the site only, with Chrome sync off |
| 21 | `claude -p --chrome` uses "the" Chrome | Every Mac whose Chrome has the Claude extension connects to the same account. A headless run sees "2 connected browsers, none selected", cannot ask, and stops | Pin one browser device id per Mac in a file outside git, and make the job prompt select that id or stop |
| 22 | `ssh mini '...set -- $x...'` splits a string into words | The mini's login shell is zsh, which does not word-split unquoted variables. Chrome started with one garbled `--user-data-dir` and made wrong, nested profile folders | Run remote multi-line logic as `ssh host 'bash -s' <<'EOF'` with explicit arguments, never as a zsh one-liner with unquoted variables |
| 23 | `"${ARR[@]}"` is safe on an empty array | macOS `/bin/bash` 3.2 with `set -u` treats an empty array as unbound. It killed `move-job.sh` right after the laptop copy was stopped, and the same bug made a job fail on every run. The first fix covered the `for` loop but missed a later `${STATE[*]}` | Use `${ARR[@]+"${ARR[@]}"}` and `${ARR[*]+"${ARR[*]}"}` everywhere. A move must start on the target before it can fail on the source, so check `launchctl list` on both Macs after every move |
| 24 | `( ... || fail )` counts failures | It runs in a subshell, so the counter in the parent never changes: 14 failures still printed ALL PASS | Never count failures inside a subshell. Use a plain loop with `if cmd; then pass; else fail; fi` |
| 25 | `sudo npm -g` leaves my npm cache alone | It left a root-owned `~/.npm` that broke every later `npm ci` as the normal user | `sudo chown -R "$(id -u):$(id -g)" ~/.npm` after `sudo npm` and before `npm ci` |
| 26 | My repo list is complete | Nested repos exist deeper than expected (down to depth 6), and one skills repo sat on an unmerged feature branch, so the mini did not match the laptop | Sweep with `find ~ -name .git` with no depth limit, and check that every job's entry path exists on the target |
| 27 | A fresh clone has everything a job needs | Re-send protection is gitignored: state files, ledgers, queues and "already sent" keys do not travel with a clone | `move-job.sh --state` copies them. List the state paths of every job before you move it |
| 28 | A 15-minute `git pull --ff-only` is a fine way to deploy to the mini | It ships untested code within 15 minutes, and it fails silently when a job writes to a tracked file | Pull by hand, or pull a gated deploy ref that CI moves. Never auto-pull senders |
| 29 | "git fetch and not behind" in a prompt gates a deploy | It is prose: the model can read "behind" and deploy anyway | Gate in code: a preflight script that exits non-zero, wired in front of the deploy |
| 30 | A bare `node job.mjs --dry` on the mini proves the move | It printed "credentials missing" for every item, because a hand-run does not load `~/.env` (the job wrapper does) | Test a moved job with the environment its wrapper loads (`set -a; . ~/.env; set +a`) before calling it broken |
| 31 | `cmd \   # comment` keeps a multi-line command intact | A comment after a trailing backslash escapes the space, not the newline, so the next line ran as its own command (exit 127). `bash -n` does not catch it | Put the comment on its own line above the command |
| 32 | A pause script can remove itself after it boots itself out | It booted itself out BEFORE its `rm` line, so it never deleted itself and re-loaded every plist each night, undoing the move | In a self-removing script, delete the plist BEFORE `launchctl bootout` |
| 33 | `git add a b c` in a loop over repos stages what exists in each | One missing pathspec makes `git add` stage nothing, and `2>/dev/null` hid the error, so the result was "nothing to commit" | Add files per repo, and never silence git errors in a multi-repo loop |
| 34 | After a multi-repo push, "push=ok" means it worked | The `$?` in the status line was the wrong command's. Two pushes were rejected because the remote was ahead | Verify with `git rev-list --count ${u}..HEAD` and `HEAD..${u}` per repo, never with the exit status of a compound line |
| 35 | `cmd1 ; cmd2 && git commit` commits only valid files | A validator's non-zero exit did not stop the chain, so invalid files were pushed | Gate every commit on the validator with `set -e` or an explicit `|| exit` |
| 36 | The mini stays up during setup | It restarted on its own about 14:15 (cause unknown, possibly an update finishing). With FileVault on it waited at the unlock screen until someone logged in, and no jobs ran | Keep the after-restart check in the runbook ("Reboots"), alert on missing runs, and plan the unlock |
| 37 | Desktop-app integration of a password manager is fine for jobs | Desktop-app integration made `op read` (1Password CLI) hang in headless jobs | Jobs use a service account token only. Check the rate limit of reads before you render a whole env file item by item |
